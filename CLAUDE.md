# Cadence (formerly LOCKIN)

Productivity PWA in React + Vite + TypeScript on Firebase Auth, Firestore and Hosting. P0 (Today, Tasks, Calendar, Focus, Habits) and P1 (gamification, analytics, social, focus rooms, Kanban and templates) are built; only the AI coach still shows as "Soon". Live at https://lockin-habits-aerosalu.firebaseapp.com (project `lockin-habits-aerosalu`); use that address, not `.web.app`, because it matches `authDomain`.

The app was renamed from LOCKIN to Cadence on 2026-11-14. Only what people see changed: the Firebase project, URL, repo, `lockin.*` localStorage keys, badge and mission IDs (such as `first-lock-in`) and code names like `lockInDays` keep the old name on purpose, so stored data and installed apps keep working. Don't use "Lock in" in UI copy.

## Rules

- The app must stay free: only use what Firebase's Spark plan includes. No SMS, Cloud Functions, or anything needing billing.
- XP, levels, streaks and scores are derived from stored records in pure functions, never stored, so they stay testable and can't be double-claimed.
- Writes are not awaited by screens: Firestore's offline cache updates listeners at once and syncs later, so awaiting would hang without signal. Only attach `.catch` to report failures.
- Motion is calm and never bouncy: use the `--dur-*` and `--ease-*` tokens in CSS and `src/design/motion.ts` in Motion, never literal timings. Motion (`motion`) is used through `import * as m from 'motion/react-m'` under `LazyMotion strict` in `App.tsx` (plain `motion.*` components throw there). Screens change through `PageTransition` (tabs crossfade, deeper paths push, Back reverses, scroll restored on Back); shared elements use `layoutId` (`focus-ring` links Today, focus mode and the summary; `habit-card-<id>` links a habit's card or row on Habits to the top of its page; `tab-pill` is the phone tab highlight; segmented controls and the calendar's chosen day use a gliding `layoutId` pill or ring). The Focus page's idle ring also carries `focus-ring`. Calendar months and weeks slide by direction inside `AnimatePresence`, and analytics periods crossfade with the `.swap` class; charts never animate their values. Phone sheets drag down to close (`Dialog`). List rows use the global `.enter` class with `--i` set to their index; `useFlip` (`src/components/useFlip.ts`) glides re-sorted rows. Entrances use `backwards` fill only, because a filling animation would override the inline transforms `useFlip` sets. `Dialog` and the toast play exit animations before unmounting. Reduced motion zeroes every duration and delay. A hidden Browser pane freezes the animation clock, so check motion with the pane shown.
- Firebase's sign-in handler lives under `/__/`; the service worker must never serve the app shell there (the `NavigationRoute` denylist in `src/sw.ts`).
- The design system is documented in `docs/design-system.md` (tokens, audit, and the phased Apple-inspired refinement). Use its tokens for type (`--text-*`, `--weight-*`, `--font-display` for headings), spacing, corners (`--radius-*`, `--radius-sheet` for dialogs) and motion; never literal sizes, weights or timings. Progress colours are `--ring-focus/tasks/habits` everywhere. `.glass` is only for floating navigation, sheets, toasts and contextual controls. Shared pieces: `Tick` (drawn when its button is `aria-pressed`), `Ring` (progress rings, labelled), `ui.switch` for on/off settings, `aria-busy` on a button for its spinner, `aria-invalid` on an input for the error state, `toast(message, { label, run })` for Undo, `PageSkeleton` while a page loads, `EmptyState` (icon, title, one sentence, one action; `compact` inside cards) for anything empty, `useFlash` + `data-saved` for a button that stays on screen after saving, and `haptic('tap'|'success')` (`src/design/haptics.ts`, Android only, off per device in Settings) on completions. The shared `spring` is critically damped: nothing overshoots.
- Text colours (`--text`, `--muted`, `--faint`, `--accent`, and the status colours) are at least 4.5:1 on `--bg` and `--card` in both themes; check contrast when changing any of them. Under reduced motion every animation runs once (`animation-iteration-count: 1`), so endless ones stop rather than flicker.
- Use the design tokens in `src/styles/global.css`, never raw colors (tints come from the `--*-soft` tokens or `color-mix` on a token). Colours are graphite neutrals plus one indigo `--accent`, used only for primary actions, progress, ticks and the active item; status colours only carry meaning. Dark is the default; light comes from `prefers-color-scheme` or the per-device Theme setting (`src/app/theme.ts`, `data-theme` on <html>, mirrored by an inline script in `index.html` so there is no flash). Any token change goes in all three blocks (dark, media light, `[data-theme=light]`). Selections (chips, day pickers) use the soft style (`--accent-soft` with an accent border and text); solid indigo is only for primary buttons, ticks and today's date. In the installed app, `--statusbar` paints a strip behind the iPhone status bar so its always-white clock stays readable in light theme.

## Commands

- Dev: `npm run emulators` in one terminal, `npm run dev` in another, then open http://127.0.0.1:5173 (not `localhost`: Google sign-in by redirect fails across the two hostnames). `.env.development` points dev at the `demo-lockin` emulators, never the live project.
- Test: `npm test` (Vitest, `src/**/*.test.ts`); one file with `npx vitest run src/lib/habits.test.ts`, one test with `-t "name"`
- Security rules tests: `npm run test:rules` (`tools/test-rules.cjs`). It starts its own Firestore emulator on port 8181 (`firebase.rules-test.json`) and runs `tests/rules/` against `firestore.rules`, so the dev emulator's data is untouched. On Windows `emulators:exec` leaves the emulator's Java process running, so the wrapper stops any Firestore emulator on 8181 before and after the run. Add a test for every rule change, covering owner, friend and stranger cases.
- Rules gotcha: in a rules path, `$(x)` inserts one segment, so build paths in full (`/databases/$(database)/documents/usernames/$(name)`), not from a joined string. The dev emulator hot-reloads `firestore.rules` and can catch a half-finished edit; re-save the file if it starts reporting unknown functions.
- Lint and type-check: `npm run lint`, `npm run build`
- Icons: `node tools/make-icons.cjs` (writes `public/icons/`)
- Deploy: `firebase deploy` (its predeploy runs `npm run build`; Hosting serves `dist/` with an SPA rewrite, and `sw.js` and `index.html` are served `no-cache` so updates reach installed apps)

## Architecture

- `src/firebase.ts` creates the app, auth and Firestore (persistent multi-tab cache) from `VITE_FIREBASE_*` env values, and connects to the emulators when `VITE_USE_EMULATORS=true`. `.env` holds the live web config, which is public by design.
- `src/app/nav.ts` is the single navigation list: `PRIMARY` (everyday screens, always in the sidebar; the first four are the phone bottom bar) and `SECONDARY` (folded under "More" in the sidebar, unfolded when one is open). The phone More page lists everything not on the bottom bar plus Settings. Entries without a `path` are later-phase modules shown as "Soon".
- The dashboard is deliberately minimal and professional: one column with the overview card (concentric focus, tasks and habits rings with a labelled legend, Start focus, this week as seven small ring sets from `weekRings`, where days with nothing due show an empty ring, and the score folded into a disclosure), one Today list (`todayList` in `src/lib/dashboard.ts` merges tasks and habits) with quick add, and the next three deadlines. Gamification (XP, levels, missions) stays off it; badge pop-ups only show when the profile's `badgeAlerts` is on.
- `src/auth/AuthProvider.tsx` combines the Firebase user and the `users/{uid}` profile document into one `AuthState`: `loading`, `signedOut`, `needsProfile` or `ready`. `App.tsx` gates on it (sign-in page, then first-time setup, then the app), so every screen inside the app can call `useSignedIn()` and rely on a profile existing.
- A missing profile is only believed once the server confirms it, not from an empty local cache, or a returning user on a new device would be sent to setup.
- Google sign-in uses a redirect on phones and in the installed app, and a popup on desktop (`src/auth/authActions.ts`). `redirectError` is read once at startup.
- Routes live in `src/app/App.tsx`, all inside `AppLayout`.
- The mark is `src/components/Logo.tsx`: a 3D ring built from stacked SVG slices with CSS `preserve-3d` (no 3D library). `animated` (splash, sign-in) orbits, floats, sweeps light and draws the check; the sidebar uses the still version, and reduced motion always gets it. Nothing on its 3D chain may use `filter`, `opacity` or `overflow: hidden`, which flatten it. `Splash` sits over the app while auth loads and fades out once it resolves. App icons are drawn by `tools/make-icons.cjs`.
- People are drawn with `src/components/Avatar.tsx` (photo, or the initial when there's none or it fails to load) everywhere: sidebar, Settings, friends, leaderboard and room members.
- Quick add reads plain words with `parseTask` (`src/lib/parseTask.ts`): dates (today, tmr, fri, next wed, in 3 days, 15 nov, nov 15, 25/12 as day/month), times (6pm, 18:30, at 6 meaning evening for 1–7, noon, tonight), `!high`/`!!`/`p1`, `#study`/`#gym`, repeats (daily, every weekday, every mon and thu, weekly) and lengths (45m, 1h30). Recognised phrases are cut out and the rest is the title; a date that doesn't exist stays in the title. No regex lookbehind anywhere in the app: Safari before 16.4 can't load a file that has one. `QuickAdd` (`src/tasks/QuickAdd.tsx`) shows what was understood as chips; Today's defaults to today, the Tasks page's to no date.
- Ctrl/Cmd+K opens `CommandPalette` (search tasks and habits, go anywhere, start focus, add the typed text as a task); `useShortcuts` adds `/` (focus the `[data-quick-add]` box), `N` (`/tasks?new=1`), `F` (start focus) and `?` (help), ignored while typing or with a dialog open. Tasks reads `?q=` and `?new` and clears them; habits open at `/habits/:id` (`HabitPage`), and the old `/habits?open=<id>` redirects there. `Dialog` focuses a child marked `data-autofocus` after `showModal`, which otherwise focuses the close button.
- The manifest (`vite.config.ts`) has home-screen shortcuts (`/focus?start=1`, `/?add=1`, handled once by `useLaunch` and then removed from the address) and a GET share target to `/share` (`SharePage`; `sharedParts` in `src/lib/share.ts` pulls a link out of shared text into the task's description). Share targets don't exist on iOS.
- Settings → Your data: `exportData` (`src/data/account.ts`) downloads everything as JSON, `tasksCsv` (`src/lib/csv.ts`, formula-safe) as a spreadsheet. Delete account needs DELETE typed and a fresh sign-in (`confirmIdentity`), then `deleteAccount` closes groups and rooms the person runs and leaves the others, deletes their shared documents (activity, cheers given and received, friendships, requests, stats, profile, username), then everything in `PRIVATE_COLLECTIONS`, then the login. Any new collection about a person must be added there; `tests/rules/account.rules.test.ts` checks the owner can find and delete each.
- Reminders while the app is closed, without Cloud Functions: `src/lib/reminders.ts` (pure, tested) works out the next 48 h of reminders from tasks with a time, habits' usual times, plan/review nudges and the 8 PM streak warning, skipping quiet hours and what's done, rounded to 15-minute UTC slots. `ReminderPlanner` (app-wide) publishes them to `pushPlans/{uid}` (`{tokens, slots, items, tz, updatedAt}`, owner-only rules) at most once a minute, using `mergeFields` so old slots don't linger and tokens aren't touched. `sender/` is a separate public repo's contents (`cadence-reminders`): GitHub Actions runs `send.mjs` every 15 minutes with a service-account secret, queries `slots array-contains <slot>`, sends data-only FCM messages, removes dead tokens and records `meta/reminderSender.lastSlot`. The service worker is our own (`src/sw.ts`, vite-plugin-pwa `injectManifest`, its own `tsconfig.sw.json`); it precaches, keeps the `/__/` denylist, shows pushes and opens the right screen on tap. Device tokens come from `enablePush` (`src/data/pushDevice.ts`, Firebase Messaging loaded on demand) and need `VITE_FIREBASE_VAPID_KEY` in `.env`; on iPhone only the installed app can receive them. Settings → Reminders holds the per-person `reminders` preferences on `users/{uid}`.
- `OfflineBar` shows a note while offline and "syncing" until `waitForPendingWrites` resolves after reconnecting.
- Shared buttons, inputs and chips are classes in `src/components/ui.module.css`; screens compose them rather than restyling controls. `Dialog` (native `<dialog>`, a bottom sheet on phones) and `useToast` are the shared overlays; the toast provider wraps the whole app.
- Layering: `src/lib/` holds pure rules with tests (no React, no Firebase); `src/data/` holds Firestore mappers, live hooks (`useUserCollection`) and write functions; feature folders such as `src/habits/` hold screens. Mappers fill gaps in stored documents so older data still loads.
- Focus: `src/lib/focus.ts` is a pure state machine over timestamps (focus, summary, break, breakOver), with `now` always passed in. `src/focus/FocusProvider.tsx` wraps the signed-in app and owns the running session: it ticks the clock, saves the state to `localStorage` so a reload resumes it (an expired phase resolves to its real end time), turns `visibilitychange` into leaves (strict mode stops a session left for over 30 seconds, at the moment of leaving), holds a wake lock, plays Web Audio ambient sound and the chime, and writes the finished session once (`saveSession` is idempotent and never touches the note). It renders `FocusOverlay` above everything while a session or break runs. Read visibility in the event handler, not inside a state updater.
- `useNow()` refreshes every minute and when the app returns to the foreground; screens derive "today" from it so day changes don't need a reload.

## Data

Private data sits under `users/{uid}/…`, which only that signed-in user can reach. Shared collections, each with its own rules and tests:
- `usernames/{name}`: `{uid}`. Created only if free and only for yourself, never updated, deleted only by its holder. This is what makes names unique.
- `profiles/{uid}`: `{username, displayName, level, photo, updatedAt}`. Readable by any signed-in user, for search. Its username must be one you hold (checked with `getAfter`, so claiming and setting share one batch in `claimUsername`). `photo` is '' or a data: WebP/JPEG of 20,000 characters or fewer (cropped and shrunk to 128 px on the device in `PhotoPicker`, since Cloud Storage needs billing) or a Google `lh3.googleusercontent.com` link; nothing else passes the rules. Writes always send the whole card, so a new field must be added to `publishProfile` and `claimUsername` together.
- `stats/{uid}`: the summary friends see (level, xp, badge IDs, this week's XP and focus minutes, `weekFocusByDay` Monday first, this month's season XP, streak, `focusing.until`, and the `bio` and up to 3 `pinned` badge IDs). The newer fields are optional in the rules so older installed versions still publish. Readable by the owner and friends (a `friendships/{lowerUid_higherUid}` document exists). Written only by the owner, with range checks. `StatsPublisher` writes it at most every 30 s and only once a username exists. Weekly totals come from `xpBetween` in `src/lib/social.ts`, which follows the same rules as the total.

- `friendRequests/{from_to}`: `{from, to, fromUsername, fromName, toUsername, status: pending|declined, createdAt}`. Only the sender creates it (the recipient needs a profile and they mustn't already be friends). It's visible to both. Only the recipient can decline; either can delete it.
- `friendships/{lowerUid_higherUid}`: `{members (sorted), since}`. It can only be created by the recipient of a pending request from the other person, in the same batch that deletes the request (`acceptRequest`). Either member can delete it.
- `activity/{uid_kind_…}`: `{uid, kind: task|habit|badge|level, title, at}`, readable by the owner and friends. IDs are fixed per thing (`activityIds` in `src/lib/friends.ts`), so reposting overwrites and undoing deletes. Deleting an ID that was never posted is allowed under your own prefix, so undo never fails. Shared tasks and habits (`shared: true`) post inside the same batch as completion and remove inside reopen and untick (`completeTask`, `reopenTask`, `logHabit`, `unlogHabit`). `AchievementPoster` posts badges and level-ups when Share achievements is on. Feed queries go per friend (`where uid == x`), which is what the rules can check.
- `cheers/{activityId_uid}`: `{activityId, owner, uid, emoji, at}`, one reaction (👏 🔥 💪 🎉) per person per activity item. The giver can read their own (for export and deletion). Only a friend of the owner can create one, on an activity that exists with that owner, and never on their own items; the cheerer can change or delete theirs, the owner can delete any on their items. Readable by the owner and their friends, loaded per owner (`where owner == x`) beside each feed source. `FeedRow` (`src/friends/FeedRow.tsx`) draws an item with its cheers on both the Friends feed and the friend page.
- Friend page (`/friends/:uid`, `src/friends/FriendPage.tsx`): photo, bio, stats, pinned badges, this week's focus chart (`weekColumns` from `stats.weekFocusByDay`), recently shared items with cheers, and Remove friend. Non-friends see a short note instead; nothing is read until the friendship is confirmed.

- `groups/{gid}`: `{name, ownerUid, code, targetMinutes, createdAt}`, readable by members. Only the owner can rename it or change the target; the code never changes.
- `groups/{gid}/members/{uid}`: the member's name, username, the group `code` (it must match the group's code on create, which is how invite codes are enforced), `joinedAt`, and a copy of their weekly numbers. Each member writes only their own; the owner can remove members. `StatsPublisher` keeps these copies current for every group in `users/{uid}/groups`.
- `groupCodes/{CODE}`: `{groupId, name}`. Single gets only, no listing, so knowing a code is what lets you find a group. Codes are 6 characters with no 0/O or 1/I. A group, its code, the owner's membership and the owner's private `users/{uid}/groups/{gid}` record are written in one batch (`createGroup`), retrying with a new code if one is taken.
- Deleting a group leaves members' private records behind; their app sees the group document missing (confirmed by the server, not the cache) and offers to remove it. `useLiveDocs` and `useLiveQuery` retry a refused listen a few times, because a read can race the write that grants access.

- `rooms/{rid}`: `{name, hostUid, code, goalMinutes, session: {startedAt, endsAt, minutes} | null, createdAt}`. Members can read it; only the host renames it, sets the goal, or starts and ends the shared session.
- `rooms/{rid}/members/{uid}`: `{uid, displayName, username, code, joinedAt, state: idle|focusing|break, heartbeatAt, minutes}`. Names and states only, never what anyone works on. Joining needs the room's code. You update only your own; `minutes` can only rise, by at most 240 per write.
- `roomCodes/{CODE}` and `users/{uid}/rooms/{rid}` work like the group ones.
- Presence: `RoomPresence` (mounted app-wide) sends a heartbeat every 60 s for the room of a running room session, or else the room page that's open (`src/rooms/viewing.ts`); anyone silent for over two heartbeats shows as away. Joining a shared session calls `focus.start(plan, endsAt)` so everyone finishes together. Sessions saved from a room carry `roomId`, and the member's `minutes` is set to the total of their sessions in that room (a total, not an increment, so a reload can't double-count).

Everything else is closed by default. `dayKey` is the device's local YYYY-MM-DD date, and timestamps are ISO strings from the device clock so offline actions keep their real time.

- `users/{uid}`: profile (`displayName`, `dailyFocusGoalMinutes`, `createdAt`, `username`, `shareAchievements`, `badgeAlerts`, `photo`, `bio`, `pinned`). The private copies are what Settings edits (`setPersonal`); `StatsPublisher` copies the photo to the public card and the bio and pins (only earned ones) into stats.
- `habits/{id}`: `name`, `category`, `schedule` (`{type:'days', days}` with `Date.getDay` numbers, or `{type:'count', perWeek}`), `usualTime`, `targetNote`, `archived`, `createdAt`
- `habitLogs/{habitId_dayKey}`: `habitId`, `dayKey`, `completedAt`, `note`. The ID allows one per habit per day and makes undo a delete.
- `tasks/{id}`: `title`, `description`, `category`, `priority` (urgent, high, medium, low), `status` (todo, in_progress, done), `dueDate` (day key or ''), `dueTime` ("HH:MM" or ''), `subtasks` (array of `{id, title, done}`), `recurrence` (`{type:'none'|'daily'|'weekly'}` or `{type:'custom', days}`), `estimateMinutes`, `order`, `createdAt`, `completedAt`, `nextTaskId`
- `sessions/{id}`: `taskId`, `habitId`, `title`, `preset`, `plannedMinutes`, `minutes` (focused, excluding pauses), `pausedMinutes`, `startedAt`, `endedAt`, `dayKey`, `outcome` (completed or stopped), `leaves` (`{at, seconds}` each time the app went to the background), `note`. Sessions under a minute aren't saved.

- `days/{dayKey}`: `{plannedAt, reviewedAt, rating 0–5, note ≤ 500, wins ≤ 3}`; `weeks/{monday}`: `{reviewedAt, note, focus ≤ 3 task IDs}`. Written with merge so planning, the evening review and the weekly review each touch only their own fields. A week's `focus` is picked in the previous week's review and shown at the top of Today.
- `taskTemplates/{id}`: `name`, `title`, `description`, `category`, `priority`, `steps` (subtask titles), `estimateMinutes`, `recurrence`. Built-in starters live in `src/lib/templates.ts`, not Firestore.

Board and order (`src/lib/board.ts`, `src/tasks/TaskBoard.tsx`): `order` is a plain number; a move writes only the moved task, at the midpoint of its new neighbours (±1024 at an end). Board moves go through `moveTask`, which routes into and out of Done via `completeTask`/`reopenTask`. Drag uses @dnd-kit with mouse, a 250 ms touch long-press, and keyboard sensors, plus a "Move to" menu on every card; screen-reader announcements are customised to use task titles, never the library's IDs.

Repeating tasks keep one live instance. Completing one creates the next in the same batch (`completeTask` in `src/data/tasks.ts`) and records its ID in `nextTaskId`; reopening deletes that next instance unless it has been worked on. Any status change into or out of done must go through those two functions, not a plain update.

Dashboard rules (`src/lib/dashboard.ts`), all derived on read:
- Lock-in day: any completed focus session, habit tick or completed task. The streak counts consecutive days; today extends it but can't break it.
- XP: 10 per completed task (once per task, lost if reopened), 10 per habit tick, 20 per completed session (capped at 8 a day; stopped sessions earn nothing), 50 per day where everything due was done on time (tasks finished late never earn their day the bonus). Level n needs 100·n more XP than level n−1.
- Gamification (`src/lib/game.ts`, `achievements.ts`, `missions.ts`): `indexGame` sorts and indexes the records once; badges are checks that return progress and the day earned; daily missions (3) and the weekly challenge are picked by a seed of uid and date, from candidates decided by records made before that day so picks never change mid-day; their XP (15 each, +30 for all three, 100 per challenge) is recomputed over every active day and passed into `xpBreakdown`. `src/game/useGame.ts` does all of this once per data change; `BadgeWatcher` announces new badges, storing only already-announced IDs per device.
- Analytics (`src/lib/analytics.ts`): day, week (Monday to Sunday) or month ranges, each compared with the previous one; habit rates expect each scheduled day for exact-day habits and the weekly number spread over the days for weekly-count ones (left out of single days); the report sentences only state what the numbers show. Charts in `src/analytics/charts/` are hand-drawn SVG that follow the dataviz skill: one axis, columns ≤ 24px with a 4px rounded top, hairline grid, a tooltip per column on hover and focus, a "Show data" table, and colours from the `--cat-*` and `--heat-*` tokens (validated against `--card`; re-run the skill's validator if you change them).
- Planning (`src/lib/plan.ts`, `src/plan/`): `todayPrompt` shows one card on Today: the weekly review on Sunday or Saturday from 6 PM until that week is reviewed, the evening review from 6 PM until the day is reviewed, else planning until 2 PM until the day is planned. `/plan` picks tasks into today (`setDue`; unpicking leaves a task undated, except repeating ones) and times them on a timeline, warning when estimates exceed the minutes left before 10 PM; its Review mode moves each open task to tomorrow, a date or no date (repeating tasks keep a date), and saves a rating, wins and a note. `/review` covers this week at the weekend, otherwise last week (`reviewWeekStart`), using `summarize` and `report` from analytics.
- Productivity score: 40% focus goal, 35% tasks due today or overdue, 25% habits due; a part with nothing due hands its weight to the others.

Streak rules (`src/lib/habits.ts`): exact-day habits count scheduled days in a row; weekly-count habits count weeks reaching the number; a day or week still in progress can extend a streak but never breaks it.

## Roadmap

Later phases from the product blueprint, each to be planned and approved before building, one reviewed step at a time:

- **P1 Gamification:** badges and daily missions as checks on the data (never stored), weekly challenges, personal bests.
- **P1 Analytics:** daily, weekly and monthly reports, focus trends, best time of day, time by category.
- **P1 Social:**
  - public profiles with unique usernames, friends, private groups, weekly leaderboards built from self-reported totals
  - focus rooms using Firestore for the room and Realtime Database presence with `onDisconnect`
  - rooms show who is focusing without task details
- **P1 Tasks extras:** Kanban with drag and drop, templates, manual ordering via `order`.
- **P2 (parked on 2026-11-15 at the user's request):**
  - **AI coach:** Firebase AI Logic on the Gemini free tier with App Check. It only suggests, and the user approves each change. Check Spark support first.
  - **Distraction blocker:** a Chrome/Edge extension in `extension/`, signalled by the app during a session.

Free-plan limits that shape these: reminders while the app is closed go through the GitHub Actions sender rather than Cloud Functions (so they can arrive up to 15 minutes late, and the app must be opened every couple of days to extend the 48-hour plan), a web app can't block other apps or sites, and leaderboards can't be server-verified.
